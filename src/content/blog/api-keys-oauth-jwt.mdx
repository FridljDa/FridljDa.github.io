## TL;DR
"API keys, OAuth or JWT?" sounds like a choice between three options, but each sits on a different layer. An **API key** is a credential: a long-lived secret sent with every request. **OAuth 2.0** is a protocol for *getting* a credential: you trade a secret you hold for a short-lived access token with limited scopes, either as yourself (client credentials) or for a person who agreed to it (authorization code). A **JWT** is a *format* a token can take: signed JSON the API can check without asking anyone. OAuth access tokens are often JWTs, which is why the three get mixed up. As the one calling an API, I need to know which credential it wants, how to get and renew it, and how to keep it out of places it doesn't belong, the model's context included.

## One agent, three systems

The running example is the invented Northstar Bank from my posts on support automation. Alex Carter writes in that their account is locked. To help, the support agent calls three systems:

- the **ticketing system**, to open an escalation
- the **CRM**, to look up Alex's account and its security flag
- **the calendar of Alex's personal advisor**, to book a callback.

Each wants a different credential, and the sections below go through them in that order.

The model never sees any of them. It picks a tool and its arguments, like `lookup_account(account_number="NSB01234")`, and the tool's code attaches the credential and makes the call. Nothing a [prompt injection](/post/prompt-injection) could extract enters the model's context.

## API keys: one secret, one header

<AuthMap preset="api-key" />

<AuthFigure name="api-key" />

*One handover, then one call per request. Nothing to fetch, nothing that expires.*

The ticketing system's admin generates a key in its settings page and gives it to us (1). From then on, every request carries it (2):

```http
POST /v2/tickets HTTP/1.1
Host: api.ticketing.example.com
Authorization: Bearer tk_live_4f9a...e21c
Content-Type: application/json

{"subject": "Locked account, security flag set", "customer_id": "NSB01234", "priority": "high"}
```

Some APIs want it in a custom header (`X-API-Key`) or as the username of HTTP Basic auth; the docs say which. The server looks the key up (3) and opens the ticket (4). Nothing to fetch, nothing expires mid-conversation, and a `curl` with one header works. The costs come from the same simplicity:

- **It identifies an application, not a person.** The ticket is created "by the integration", whoever the agent is talking to.
- **It lives until someone rotates it.** A key leaked into a log or a Git commit keeps working until someone notices.
- **It is often all-or-nothing.** Some platforms let you scope a key to read-only or one project; many don't.
- **It goes in a header, never in the URL.** Query strings end up in proxy logs and browser history.

A fine fit when the calling application *is* the actor, the key lives in a secrets manager, and the API offers nothing better.

## OAuth 2.0: trade a secret for a short-lived token

[OAuth](https://datatracker.ietf.org/doc/html/rfc6749) fixes the long-lived part with a middleman, the **authorization server**. The client, our agent's tools, sends its long-lived secret only there, once in a while, and gets back an **access token**: valid for minutes to an hour, and limited to the **scopes** that were granted, like `contacts.read`. The API, the **resource server**, only ever sees the access token.

How the client gets the token is the **grant type**. Two cover almost every integration.

### Client credentials: the agent as itself

<AuthMap preset="client-credentials" />

The CRM integration has no human in it: the agent reads accounts as itself. The CRM admin registers our agent as a client, and the CRM's admin console shows two values:

<CodeMarks marks={{ 'northstar-support-agent': 'orange', 'q8Zr2vLx7TfN4mKd9WbE': 'purple' }}>

```text
client_id:     northstar-support-agent
client_secret: q8Zr2vLx7TfN4mKd9WbE
```

</CodeMarks>

The <Mark c="orange">client_id</Mark> names the client and is not a secret: it shows up in logs, and in the calendar flow below, in the browser's address bar. The <Mark c="purple">client_secret</Mark> is the password. Consoles often show it only once, so it goes straight into the secrets store.

<AuthSteps name="client-credentials" caption="Two calls to get going: one to the auth server for a token, one to the API with it. After that, only the second, until the token expires.">

The token request (1) is a form-encoded `POST`. The client authenticates with HTTP Basic: the two values joined by a colon, <Mark c="orange">northstar-support-agent</Mark>:<Mark c="purple">q8Zr2vLx7TfN4mKd9WbE</Mark>, then <Mark c="teal">base64-encoded</Mark>:

<CodeMarks marks={{ 'bm9ydGhzdGFyLXN1cHBvcnQtYWdlbnQ6cThacjJ2THg3VGZONG1LZDlXYkU=': 'teal' }}>

```http
POST /oauth/token HTTP/1.1
Host: auth.crm.example.com
Authorization: Basic bm9ydGhzdGFyLXN1cHBvcnQtYWdlbnQ6cThacjJ2THg3VGZONG1LZDlXYkU=
Content-Type: application/x-www-form-urlencoded

grant_type=client_credentials&scope=contacts.read%20cases.write
```

</CodeMarks>

Base64 is there for transport, not secrecy: a header may only carry plain ASCII characters, and base64 turns any ID and secret into those, in a form the server decodes back. It is an encoding, not encryption: whoever sees that header has the secret. That is why it only ever travels over HTTPS, and only to the token endpoint.

The answer (2) holds the <Mark c="blue">access token</Mark> and how long it lasts, <Mark c="amber">expires_in</Mark>:

<CodeMarks marks={{ 'eyJhbGciOiJSUzI1NiIsInR5cCI6IkpXVCIsImtpZCI6ImNybS0yMDI2LTEwIn0.eyJpc3Mi...': 'blue', '"expires_in": 3600': 'amber' }}>

```json
{
  "access_token": "eyJhbGciOiJSUzI1NiIsInR5cCI6IkpXVCIsImtpZCI6ImNybS0yMDI2LTEwIn0.eyJpc3Mi...",
  "token_type": "Bearer",
  "expires_in": 3600,
  "scope": "contacts.read cases.write"
}
```

</CodeMarks>

<Mark c="amber">expires_in</Mark> is seconds from now, not a time of day, so the two machines' clocks don't have to agree. It doesn't decide when the token expires: the auth server does, and after that the API answers `401`. It tells the client how long it can count on the token, so it can fetch the next one in time.

Every CRM call (3) then carries the <Mark c="blue">access token</Mark>:

<CodeMarks marks={{ 'eyJhbGciOiJSUzI1NiIsInR5cCI6IkpXVCIsImtpZCI6ImNybS0yMDI2LTEwIn0.eyJpc3Mi...': 'blue' }}>

```http
GET /v2/contacts?account_number=NSB01234 HTTP/1.1
Host: api.crm.example.com
Authorization: Bearer eyJhbGciOiJSUzI1NiIsInR5cCI6IkpXVCIsImtpZCI6ImNybS0yMDI2LTEwIn0.eyJpc3Mi...
```

</CodeMarks>

The CRM API checks it without asking the auth server each time: it fetches the auth server's public keys once (4, 5) and checks the JWT with them (6), as [the next section](#the-crms-token-is-a-jwt) shows. Then it answers (7):

```http
HTTP/1.1 200 OK
Content-Type: application/json

{"account_number": "NSB01234", "name": "Alex Carter", "status": "locked", "security_flag": "suspicious_login"}
```

Two things are easy to get wrong:

- **Cache the token.** A fresh one per call doubles the latency, and auth servers rate-limit the token endpoint. Keep it until shortly before `expires_in` runs out, and fetch a new one on a `401`.
- **No refresh token here.** The agent still has its client secret, so it just asks again.

The `client_secret` is long-lived too, so this can look like an API key with extra steps. What OAuth buys: the secret travels to one endpoint occasionally rather than on every call, what *does* travel expires, and it carries scopes.

</AuthSteps>

### The CRM's token is a JWT

<AuthMap preset="jwt" />

The CRM's access token starts with `eyJ`, base64 for `{"`: it is a [**JSON Web Token**](https://datatracker.ietf.org/doc/html/rfc7519), three base64url parts separated by dots.

<AuthFigure name="jwt" />

*The CRM's access token, decoded. The claims are what the API checks; the signature is why it can trust them.*

The payload's fields are **claims**: `iss` who issued it, `sub` who it is about (our agent here, a user in a delegated flow), `aud` which API it is for, `exp` when it expires, `scope` what it allows.

The signature is what JWTs buy: the API verifies the token with the auth server's public key, **without asking anyone**. It fetches the keys once, as a **JWKS** (JSON Web Key Set) at a well-known URL, and picks the one the token's header names as <Mark c="teal">kid</Mark>. These are steps 4 to 6 above:

```http
GET /.well-known/jwks.json HTTP/1.1
Host: auth.crm.example.com
```

<CodeMarks marks={{ '"kid": "crm-2026-10"': 'teal' }}>

```json
{
  "keys": [
    {
      "kid": "crm-2026-10",
      "kty": "RSA",
      "alg": "RS256",
      "use": "sig",
      "n": "u1SU1LfVLPHCozMxH2Mo4lgOEePzNm0tRgeLezV6ffAt0gunVTLw7onLRnrq0_IzW7yWR7QkrmBL7jTKEn5u...",
      "e": "AQAB"
    }
  ]
}
```

</CodeMarks>

`n` and `e` are the RSA public key. Publishing it is safe: it can check signatures, not make them.

- **Signed, not encrypted.** Anyone holding the token can read the claims. No secrets go in them, and until `exp` the token is as good as a password to whoever holds it.
- **Can't be taken back.** A leaked JWT stays valid until `exp`. That is why access tokens are short-lived, and the long-lived trust sits in something the auth server checks on every use: the client secret here, the refresh token in the calendar flow below. An **opaque** token, a random string the API checks by asking the auth server ([introspection](https://datatracker.ietf.org/doc/html/rfc7662)), is revocable at once, at the cost of a lookup per request. The calendar's tokens below are opaque.
- **Not meant for the caller.** The agent calling the CRM doesn't need to decode its token: it is addressed to the API, and the provider may change its format. Decoding it is still the fastest way to debug a `403`: the `scope` or `aud` is usually wrong.

#### If you run the API: checking one

Step 6 in code. Verifying a JWT is more than checking the signature. With [PyJWT](https://pyjwt.readthedocs.io/):

<CodeMarks marks={{ 'algorithms=["RS256"]': 'blue', 'audience="https://api.crm.example.com"': 'orange', 'options={"require": ["exp", "iss", "aud"]}': 'teal' }}>

```python
import jwt  # PyJWT

jwks = jwt.PyJWKClient("https://auth.crm.example.com/.well-known/jwks.json")

def verify(token: str) -> dict:
    signing_key = jwks.get_signing_key_from_jwt(token)  # picks the key by "kid"
    return jwt.decode(
        token,
        signing_key.key,
        algorithms=["RS256"],                    # never trust the token's own "alg"
        audience="https://api.crm.example.com",  # minted for this API, not another one
        issuer="https://auth.crm.example.com",   # by the server we trust
        leeway=30,                               # tolerate small clock skew
        options={"require": ["exp", "iss", "aud"]},
    )
```

</CodeMarks>

- **<Mark c="blue">algorithms</Mark>** pins the algorithm. Early libraries trusted the header, so an attacker could set `"alg": "none"` and drop the signature, or switch `RS256` to `HS256` and sign with the *public* key as if it were a shared secret. The [JWT best practices](https://datatracker.ietf.org/doc/html/rfc8725) describe both.
- **<Mark c="orange">audience</Mark>** stops a token minted for the ticketing API from being replayed against the CRM.
- **<Mark c="teal">require</Mark>** rejects tokens that leave `exp` out and would otherwise never expire.

#### Where else JWTs show up

- **As the client's credential.** Some providers replace the `client_secret` with a JWT the client signs with its own private key ([RFC 7523](https://datatracker.ietf.org/doc/html/rfc7523)). Service accounts on large cloud and CRM platforms work like this: nothing reusable travels at all.
- **As an ID token.** [**OpenID Connect**](https://openid.net/specs/openid-connect-core-1_0.html) adds login on top of OAuth: the auth server also returns an **ID token**, a JWT that tells the *client* who the user is. The access token is for the API, the ID token for the client; sending an ID token to an API is a classic mix-up.

### Authorization code: the agent on someone's behalf

<AuthMap preset="auth-code" />

The second grant is for the calendar, which belongs to the advisor. The agent shouldn't hold a key to *every* advisor's calendar; it should act for the advisors who agreed to it, on their calendars only. This delegation is what OAuth was built for, and the flow behind every "Allow this app to…" screen: the **authorization code** grant.

<AuthSteps name="authorization-code" caption="The advisor is in the loop once, for steps 1 to 5. Everything after happens between our backend and the auth server.">

It starts in our app: the advisor clicks "Connect calendar" (1). Before answering, the backend makes up two random values for this one login (2) and keeps them in the advisor's session:

- **<Mark c="teal">state</Mark>** goes along as it is. When the code comes back, the backend checks it matches, so an attacker can't splice their code into someone else's session.
- **[PKCE](https://datatracker.ietf.org/doc/html/rfc7636)**: a <Mark c="blue">code_verifier</Mark>, of which only the hash, the <Mark c="blue">code_challenge</Mark>, goes along now. The verifier itself only travels in step 7, so only whoever started the flow can finish it. Current best practice asks for PKCE on every client.

Then it answers with a redirect (3), a `302` whose `Location` sends the advisor's browser on to the calendar provider's auth server, here with one parameter per line:

<CodeMarks marks={{ 'state=Xq7pV2mL9sKw': 'teal', 'code_challenge=E9Melhoa2OwvFrEMTJguCHaoeK1t8URWbuGJSstw-cM': 'blue', 'code_challenge_method=S256': 'blue' }}>

```text
https://auth.calendar.example.com/authorize
  ?response_type=code
  &client_id=northstar-support-agent
  &redirect_uri=https://agent.northstar.example.com/oauth/callback
  &scope=calendar.events.write
  &state=Xq7pV2mL9sKw
  &code_challenge=E9Melhoa2OwvFrEMTJguCHaoeK1t8URWbuGJSstw-cM
  &code_challenge_method=S256
```

</CodeMarks>

The advisor logs in and approves (4) at the calendar provider, never at our app. We never see their password.

The auth server sends the browser back to our `redirect_uri` with a <Mark c="orange">code</Mark> and the same <Mark c="teal">state</Mark> (5):

<CodeMarks marks={{ 'code=SplxlOBeZQQYbYS6WxSbIA': 'orange', 'state=Xq7pV2mL9sKw': 'teal' }}>

```text
https://agent.northstar.example.com/oauth/callback?code=SplxlOBeZQQYbYS6WxSbIA&state=Xq7pV2mL9sKw
```

</CodeMarks>

The backend checks the <Mark c="teal">state</Mark> against the one in the session (6) and drops it: it was only good for these few minutes.

The <Mark c="orange">code</Mark> is worth nothing on its own. Our backend trades it (7) at the token endpoint, together with its own client credentials and the PKCE <Mark c="blue">code_verifier</Mark>, so a code intercepted in the browser can't be redeemed by someone else:

<CodeMarks marks={{ 'code=SplxlOBeZQQYbYS6WxSbIA': 'orange', 'code_verifier=dBjftJeZ4CVP-mB92K27uhbUJU1p1r_wW1gFWFOEjXk': 'blue' }}>

```http
POST /oauth/token HTTP/1.1
Host: auth.calendar.example.com
Authorization: Basic <client_id:client_secret, base64-encoded>
Content-Type: application/x-www-form-urlencoded

grant_type=authorization_code&code=SplxlOBeZQQYbYS6WxSbIA&redirect_uri=https%3A%2F%2Fagent.northstar.example.com%2Foauth%2Fcallback&code_verifier=dBjftJeZ4CVP-mB92K27uhbUJU1p1r_wW1gFWFOEjXk
```

</CodeMarks>

The auth server hashes the <Mark c="blue">code_verifier</Mark> and compares it with the <Mark c="blue">code_challenge</Mark> from step 3 (8). If they match, it answers (9), with one field more than in client credentials, the <Mark c="amber">refresh token</Mark>:

<CodeMarks marks={{ '"refresh_token": "cal_rt_9KdLw3ZnQ8bY..."': 'amber' }}>

```json
{
  "access_token": "cal_at_7Hq2Lm9xPv4T...",
  "token_type": "Bearer",
  "expires_in": 3600,
  "refresh_token": "cal_rt_9KdLw3ZnQ8bY...",
  "scope": "calendar.events.write"
}
```

</CodeMarks>

Unlike the CRM's JWT, these tokens are **opaque**: random strings the calendar can only check by looking them up. The access token goes on the calendar call (10), as a bearer token like any other:

```http
POST /v1/me/events HTTP/1.1
Host: api.calendar.example.com
Authorization: Bearer cal_at_7Hq2Lm9xPv4T...
Content-Type: application/json

{"title": "Callback: Alex Carter, locked account", "start": "2026-10-27T10:00:00+01:00", "duration_minutes": 15}
```

The <Mark c="amber">refresh token</Mark> is the long-lived secret here. It goes in the secrets store, one per advisor, and an hour later gets a new access token without the advisor (11):

<CodeMarks marks={{ 'refresh_token=cal_rt_9KdLw3ZnQ8bY...': 'amber' }}>

```http
POST /oauth/token HTTP/1.1
Host: auth.calendar.example.com
Authorization: Basic <client_id:client_secret, base64-encoded>
Content-Type: application/x-www-form-urlencoded

grant_type=refresh_token&refresh_token=cal_rt_9KdLw3ZnQ8bY...
```

</CodeMarks>

Many providers **rotate** it: the answer (12) holds a <Mark c="amber">new refresh token</Mark> as well and invalidates the old one.

<CodeMarks marks={{ '"refresh_token": "cal_rt_Bw6Hs2Mk4Pz..."': 'amber' }}>

```json
{
  "access_token": "cal_at_Rt5Vn1qXc8Jw...",
  "token_type": "Bearer",
  "expires_in": 3600,
  "refresh_token": "cal_rt_Bw6Hs2Mk4Pz...",
  "scope": "calendar.events.write"
}
```

</CodeMarks>

An integration that forgets to store the new one works for exactly one hour.

</AuthSteps>

Two more grants are in the original spec, and current best practice ([RFC 9700](https://datatracker.ietf.org/doc/html/rfc9700)) says not to use them: the **implicit** grant, which returned the token in the URL, and the **password** grant, where the client collects the user's password itself.

## When a call fails: 401 or 403

<AuthMap preset="errors" />

<AuthFigure name="errors" />

*The same CRM call failing twice: once on the token, which a new one fixes, once on the scopes, which no retry fixes.*

The status code says which layer failed, as the [bearer token spec](https://datatracker.ietf.org/doc/html/rfc6750#section-3.1) defines them:

**`401 Unauthorized`: "I don't know who you are."** The token is missing, expired, malformed or signed by someone the API doesn't trust: <Mark c="orange">invalid_token</Mark> (1, 2). Fetch a new one (3, 4) and retry *once* (5, 6).

<CodeMarks marks={{ 'error="invalid_token"': 'orange' }}>

```http
HTTP/1.1 401 Unauthorized
WWW-Authenticate: Bearer error="invalid_token", error_description="The access token expired"
```

</CodeMarks>

**`403 Forbidden`: "I know who you are, and you may not do this."** A missing scope or role: <Mark c="teal">insufficient_scope</Mark>, here the agent trying to unlock Alex's account with a token that only has `contacts.read` (7, 8). A new token with the same grants won't help; the fix is in the client's configuration, usually on the provider's side.

<CodeMarks marks={{ 'error="insufficient_scope"': 'teal' }}>

```http
HTTP/1.1 403 Forbidden
WWW-Authenticate: Bearer error="insufficient_scope", scope="contacts.write"
```

</CodeMarks>

Retrying a `403` in a loop is a bug.

## Three systems, three credentials

- **Ticketing:** an API key, sent with every call. The agent acts as itself, and the key lives until someone rotates it.
- **CRM:** client credentials. The agent trades its secret for an hour-long token, a JWT the API checks on its own.
- **Calendar:** authorization code. The advisor agrees once, and the agent keeps a refresh token per advisor to get short-lived, opaque tokens for their calendar.

So the question for a new API is not which of the three to use. It is whose data the call touches, which decides the grant, and which secret our code has to keep, which decides where it is stored.
