## TL;DR
In an analysis report, the prose is where numbers go stale: a sentence still says 4.5% long after a rerun made it 4.4%. The motor-pricing analysis behind three earlier posts, on [frequency and severity](/post/frequency-times-severity), [large claims](/post/large-claim-loading) and [the model comparison](/post/tweedie-glm-vs-xgboost), is built so that can't happen. A pipeline computes everything; notebooks may only read its results; a check fails the render on any number typed into the prose; and renders are deterministic, so every change to the committed reports is a real one. Most of the code was written with a coding agent, and these checks are what make its edits safe to accept.

## The pipeline computes, the notebooks present

Every computation is a rule in a [Snakemake](https://snakemake.github.io/) workflow, from the download through cleaning, the split, one job per model and fold, the benchmark and the final model. Rules write layered data (raw, cleaned, model outputs) and, per topic, a `stats.json` and a few small tables: the only thing a report may read. All parameters, from cleaning caps to seeds, live in one config file, and Snakemake reruns a rule exactly when its inputs, parameters or code change. Changing one model's learning rate refits that model's five folds and nothing else.

*Rules write result files; notebooks only read them. Checks guard the way to the reports.*

A Quarto notebook reads through two functions, `read_stats(topic)` and `read_table(topic, name)`, then reshapes, plots and explains. Each notebook's render rule finds its inputs by scanning the notebook for the topics it reads, so a report re-renders exactly when a result it shows changes, and a render takes seconds.

## The checks

**No typed numbers.** Every number in the prose is an inline expression, evaluated at render time:

```markdown
It explains `{python} f"{d2[best]:.2%}"` of the constant model's deviance,
the Tweedie GLM `{python} f"{d2['glm_tweedie']:.2%}"`.
```

A pre-render script blanks out everything that isn't prose (code, inline expressions, math, link targets), removes a short whitelist such as years and identifiers like `log1p`, and fails the render on any digit left. Captions and Markdown tables are covered too, so they come from code. Claims about numbers are computed as well: "beats the GLM by far" is chosen from the results, so a rerun that changes the comparison changes the sentence.

**Notebooks may not compute.** A second script fails the render if a code cell reads layer data, writes a file, calls `.fit(`, imports a modelling library or calls a pipeline computation. A new number has to come from a rule, computed once with the same folds and seeds as everything else.

**Renders are deterministic.** Committed reports are only reviewable if a rerun that changes nothing changes nothing in the diff. Plotly gives every figure a random div ID, so a wrapper sets IDs from a counter; matplotlib's SVGs hash float clip boxes into their IDs, so its few figures are PNGs; tables get fixed IDs. A pre-push hook then re-renders every report from the existing results and refuses the push if the committed reports differ. CI runs the static checks: ruff with every rule on, `mypy --strict`, both notebook checks and a dry run of the pipeline.

## Why this matters with a coding agent

The conventions live in an `AGENTS.md`, written for coding agents and humans alike, and most commits were made together with one. An agent writes a paragraph around a figure quickly, and just as quickly writes into it a number it remembers from an earlier run. Here that fails the render. Asked for a new statistic in a notebook, it can't compute it there; it has to add it to a rule. Reviewing its change means reading a diff of code and a diff of rendered reports, and the second shows only what really changed.

[The Missing Test Suite](/post/the-missing-test-suite) argues that once code is cheap, the bottleneck is knowing whether the output is right. For an analysis, part of that can be made mechanical: not whether the method is sound, which still takes someone who knows the field, but whether the report says what the data say.
