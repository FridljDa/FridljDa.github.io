## TL;DR
Anthropic [advises against](https://claude.com/resources/articles/building-agents-when-to-fold-subagents-into-your-main-agent-loop) splitting an agent into subagents along team lines, and I've seen products fail that way. I've also seen the opposite fail: one team owns the agent, and every other team waits on it. Customers need one coherent conversation; teams need to ship without each other. So split ownership at build time, not at runtime: one agent loop owned by a platform team, and feature teams that contribute skills, MCP servers and eval cases without touching the model or the prompt. A shared eval gate catches what one team breaks for another, scoped so that one team's failures don't block another team's releases.

## Subagents per team: the handoffs break the conversation

The running example is invented to protect the client, but the projects behind it are real. Northstar Bank automates its first-level support. Three teams own the systems the agent needs: Accounts (logins, locks), Cards (blocks, replacements) and Payments (transfers, limits).

The obvious design gives each team its own subagent behind a router. Each team writes its own prompt, picks its own tools and ships on its own schedule. The teams are independent; the conversation isn't.

Alex Carter writes in: their account is locked, and the card they tried in the meantime was blocked too. The router has to pick one subagent, and whichever it picks hands half the problem to the other.

<TeamFigure name="handoff" />

*Accounts passes the card on, but not the lock or the account number, so Cards asks Alex for something Alex already wrote.*

Anthropic's article names the pattern: the architecture becomes "a copy of their org chart (Conway's law at work)", and information degrades "with each handoff". It also describes a system prompt where "every team adds a sentence", evals nobody owns end to end, and a single loop running about twice as fast as the multi-agent version.

## One team owns the agent: everyone else waits

The article's fix is one agent loop: one model, one context window, skills and tools loaded as needed. But one loop easily becomes one team. If the agent team owns the account lookup, the card tools and the bank's procedure for a locked account, every change in Accounts, Cards or Payments queues behind it, and the teams who know their systems best end up writing tickets. In large organisations I've seen this stop products as surely as subagent sprawl does.

Independence isn't a nice-to-have. A team that can't change its own part without coordinating with three others stops changing it. The question is how to get one loop at runtime while every team still ships on its own.

Almost all of these come from vendors or vendor-hosted blogs, Anthropic's included, and I found no independent post-mortem. They agree that central infrastructure with distributed owners works. They disagree on the price of one loop: shared tool selection and shared evals couple the teams. Shopify kept the loop and moved instructions into the tools; monday.com split it up. monday.com's post names no model, and tool selection depends heavily on the model, so your own evals on your model are better evidence than either.

## One loop, many owners

<TeamMap preset="overview" />

*The platform team owns the loop, the system prompt, the model, the gateway and the eval gate. Each feature team contributes a skill, an MCP server and eval cases.*

### Skills: how each team works

<TeamMap preset="skills" />

Accounts writes the skill for a locked account: look the customer up, never ask for what we can find, check the security flag before any unlock. The procedure lives with the team that knows it, not in a shared system prompt, and the agent loads it when a message needs it. Shopify [returns instructions with each tool's results](https://shopify.engineering/building-production-ready-agentic-systems) instead, which also keeps them with the team. But the model sees those only after calling the tool, too late to help it choose one; a skill is found before the agent acts.

### Tools: one MCP server per team

<TeamMap preset="tools" />

Accounts runs an MCP server with `accounts_lookup` and `accounts_send_unlock_link`; Cards runs one with `cards_get_status`. Each registers with a central gateway such as [LiteLLM's](https://docs.litellm.ai/docs/mcp), which handles authentication and decides which tools the agent sees, so no team builds auth itself, as an [enterprise MCP platform write-up](https://newsletter.optimistengineer.com/p/building-an-enterprise-mcp-platform-594) also argues. Behind a stable interface, a team changes its server whenever it likes. Sierra's gateway scaled once each service's owners, not a central team, configured its integration.

### Evals: the contract

<TeamMap preset="evals" />

Accounts contributes cases like Alex's, with the reply an expert would accept, to a shared eval store such as [MLflow](https://mlflow.org/docs/latest/genai/). The platform team runs every team's cases against the whole agent on every change, its own included.

## Keeping the teams independent

One loop couples the teams at runtime: they share the model's context and can break each other's conversations. Four rules keep that coupling in the test suite:

- **No sign-off for passing changes.** The platform team reviews only new tools, changed interfaces and wider access.
- **Blocked only by your own failures.** A change is blocked by its own domain's cases and a short must-not-break list, such as unlocking a flagged account. Other failures are reported to their owners, so one flaky Payments case can't stop Cards from shipping.
- **An off switch per team.** A team can disable its own tool without asking.
- **A team prefix on every tool.** `accounts_lookup`, not `lookup`, so a misfiring tool has an obvious owner.

<TeamFigure name="gate" />

*Only a change's own cases and the must-not-break set block it. A Cards change that breaks a Payments case is reported to Payments, and Cards ships.*

## What it costs

The platform team holds the prompt, the gate and the calls no single team can make, such as which of two vaguely described tools should take a request. Staff it like a product team, not one person.

The feature teams have work too. Anthropic's article notes that tool choice degrades past 30 to 50 tool definitions, so tools need descriptions by what the customer wants, not one per backend API. And a team without eval cases has no protection when another team breaks its flow; ten golden cases is a start.

## When to split after all

Split by context, not by team: a separate permission boundary, or a verifier that shouldn't see the reasoning it checks. Beyond that, measure how often a team's change breaks another domain's cases. If one domain keeps climbing, give it its own agent, exposed to the main loop as a single tool. Then the split follows the evidence, not the org chart.
