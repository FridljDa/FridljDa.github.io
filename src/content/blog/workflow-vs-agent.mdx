Progress in frontier AI models has allowed coding agents to tackle ever more complex and long-running tasks. Benchmarks are saturating fast, and the trajectory is genuinely impressive.

What makes coding agents so effective is a combination of three things. First, software is largely composed of patterns LLMs have seen countless times during training — syntax, idioms, libraries, algorithms. Second, code gives you *automated evaluation for free*. You run it, and you get a compiler error, a failing test, or a stack trace. The agent doesn't need to know whether it's right — the environment tells it. Third, and most importantly, agents can iterate cheaply. A bad attempt costs a few seconds of compute and nothing irreversible happens. In many benchmarks, coding agents are given nothing but terminal access — like [tbench](https://www.tbench.ai/) — and are left to try things, observe results, and loop until the task is done. That tight feedback loop is what allows them to crack problems that would have seemed out of reach just a year ago.

But this combination — abundant training data, automated feedback, and cheap retries — is specific to code. Most business tasks don't have any of it. There is no compiler for procurement policy. LLMs haven't seen your internal approval chains or vendor contracts during training. And placing a wrong order isn't something you can just undo and retry.

That difference is why, for business automation, my instinct has been to lean on workflows and keep the LLM on a short leash. The first half of this post makes that case with a small, clean example. The second half complicates it: in a real project I followed exactly that instinct, built the workflow, and now suspect it was the wrong default — the problem had far more combinations than any tree I could hardcode. The honest lesson turned out to be less about agents *versus* workflows than about which one you reach for first.

Let's start with the clean example.

---

## The scenario

Bob from OilVentures sends the following request to his procurement department:

> I need a new laptop for my work. I would like:
> - MacBook Pro
> - M4 Max Chip
> - 16 inch
> - 32GB RAM
> - 1TB Storage
>
> I am working in the finance department. Can you please find the best options for me and make the purchase?

OilVentures, AwesomeMarketplace, Bob, and the request are all fictional.

The procurement department handles requests like this regularly and wants to automate it. Two constraints are relevant:

- **AwesomeMarketplace** (their vendor) requires brand, model, chip, RAM, and storage to filter products.
- **OilVentures policy** caps laptop spend at **$3,000** for the finance department.

We'll look at three ways to automate this.

Across the diagrams, the notation is consistent: **🤖 Agent** means an autonomous component that chooses actions and uses tools; **🧠 LLM-assisted step** means a constrained model call with a defined output; **⚙️ Code step** means deterministic application logic; and **🔌 External tool/API** means a dependency outside the workflow.

---

## 1. The fully agentic approach

A single Procurement Agent gets access to all three tools — marketplace search, company policy, and order placement — and figures out the rest on its own.

```mermaid
flowchart TD
    INPUT(["Bob's laptop request"])
    A1["🤖 Agent<br/>procurement reasoning and tool use"]
    T1["🔌 External tool/API<br/>marketplace search"]
    T2["🔌 External tool/API<br/>company policy"]
    T3["🔌 External tool/API<br/>order placement"]
    OUT1(["Order placed<br/>notify Bob"])
    OUT2(["Order rejected<br/>notify Bob"])

    INPUT -->|"request"| A1
    A1 -->|"search products"| T1
    T1 -->|"product results"| A1
    A1 -->|"check policy"| T2
    T2 -->|"policy data"| A1
    A1 -->|"place order"| T3
    T3 --> OUT1
    A1 -->|"not compliant"| OUT2

    classDef agent fill:#f3e8ff,stroke:#7c3aed,stroke-width:2px
    classDef tool fill:#fef3c7,stroke:#d97706,stroke-width:2px
    classDef terminal fill:#f8fafc,stroke:#64748b,stroke-width:1.5px
    class A1 agent
    class T1,T2,T3 tool
    class INPUT,OUT1,OUT2 terminal
```

This looks elegant, but it has a serious problem: there is no guarantee the agent will check the policy *before* placing the order. It might. It might not. And if it places a non-compliant order, you only find out after the fact. Unlike coding tasks — where a failed test is cheap and reversible — a wrongly submitted purchase order has real consequences. As the ServiceNow CEO [put it](https://open.spotify.com/episode/11xeL3QCAF77z1vxOp0am0?si=fc70f33f0dd64ab4): people forgive other people for making mistakes. They don't forgive software.

## 2. The specialised multi-agent approach

Rather than one agent doing everything, we give each task its own dedicated agent with a single tool. Regular code orchestrates the handoffs between them, and Search and Policy agents run in parallel.

```mermaid
flowchart TD
    INPUT(["Bob's laptop request"])
    A1["🤖 Agent<br/>search products"]
    A2["🤖 Agent<br/>retrieve policy"]
    A3["🤖 Agent<br/>select and order"]
    T1["🔌 External tool/API<br/>marketplace search"]
    T2["🔌 External tool/API<br/>company policy"]
    D1{"Within the<br/>$3,000 cap?"}
    T3["🔌 External tool/API<br/>order placement"]
    OUT1(["Order placed<br/>notify Bob"])
    OUT2(["Order rejected<br/>notify Bob"])

    INPUT -->|"request"| A1
    INPUT -->|"department"| A2
    A1 -->|"query"| T1
    T1 -->|"ranked options"| A1
    A2 -->|"lookup"| T2
    T2 -->|"budget cap"| A2
    A1 -->|"options"| A3
    A2 -->|"policy"| A3
    A3 --> D1
    D1 -->|"yes"| T3
    D1 -->|"no"| OUT2
    T3 --> OUT1

    classDef agent fill:#f3e8ff,stroke:#7c3aed,stroke-width:2px
    classDef tool fill:#fef3c7,stroke:#d97706,stroke-width:2px
    classDef decision fill:#fff7ed,stroke:#ea580c,stroke-width:2px
```

This is better. Each agent has a narrow, well-defined job, and code controls the sequencing — so we know the policy check always happens before the order. But three agent invocations for what is largely a structured task still feels like overkill. The Search and Policy agents are essentially doing retrieval with a thin reasoning wrapper. We're paying the cost of LLM unpredictability where we don't need to.

## 3. The hybrid approach: LLM-assisted extraction + code workflow

The key insight is that there is only *one* genuinely hard part of Bob's request: parsing his free-text message into a structured spec the marketplace API can consume. Everything after that — the search, the policy check, the order — can be handled deterministically by regular code.

```mermaid
flowchart TD
    INPUT(["Bob's laptop request"])
    L1["🧠 LLM-assisted step<br/>extract structured specification"]
    C1["⚙️ Code step<br/>search exact product filters"]
    C2["⚙️ Code step<br/>retrieve department budget"]
    T1["🔌 External tool/API<br/>marketplace search"]
    T2["🔌 External tool/API<br/>policy store"]
    C3["⚙️ Code step<br/>select best match"]
    D1{"Within the<br/>$3,000 cap?"}
    T3["🔌 External tool/API<br/>order placement"]
    OUT1(["Order placed<br/>notify Bob"])
    OUT2(["Order rejected<br/>notify Bob"])

    INPUT -->|"free-text request"| L1
    L1 -->|"product specification"| C1
    L1 -->|"department"| C2
    C1 -->|"query"| T1
    T1 -->|"product results"| C3
    C2 -->|"lookup"| T2
    T2 -->|"budget cap"| C3
    C3 --> D1
    D1 -->|"yes"| T3
    D1 -->|"no"| OUT2
    T3 --> OUT1

```

For this bounded process, the hybrid is the best fit. Product search, budget lookup, and ordering have explicit rules and a small state space. Code makes those rules reliable and auditable; the LLM only bridges human language and structured data.

### Verify the distribution before you design

Why is this even tractable? Why isn't every request like Bob's a unique snowflake? Because real business processes rarely are. Take a sample of past procurement requests, ask a small LLM to bucket them into a few intent categories — laptops with specs, peripherals, software licences, replacement orders, vendor onboarding — and the vast majority usually fall into a handful of buckets. The long tail is real, but the head of the distribution dominates.

This isn't an assumption; it's something you verify empirically before designing the system. Cluster a few hundred historical requests and look at the coverage. If 80% of your traffic falls into a dozen well-defined intents, the hybrid approach is on solid ground. If your distribution is genuinely flat — every request its own snowflake — you have a different problem, and probably need a different architecture. Skipping this check is how teams end up building agentic monoliths for tasks that turn out to be 90% structured.

### Why workflows win here

Once the distribution checks out, code earns its place at almost every step:

- **Use code where code is enough.** The marketplace search and policy lookup rarely change. A robust integration — exponential backoff, error handling, retries — is a one-time investment, and it will be more reliable than an agent figuring out how to call them on the fly, every time.
- **Scope the LLM to what only an LLM can do.** Extracting a structured spec from free text is a well-defined task. You can build targeted evals, iterate on the prompt, drop to a cheaper model — or swap the LLM for a Named Entity Recognition model if your vocabulary is bounded enough. None of that is possible once the LLM is entangled with search, policy, and ordering.
- **Don't ask an LLM to enforce rules it hasn't seen.** Models have seen countless lines of code in training. They have *not* seen your procurement policy or vendor contracts. A budget cap is a hard `if` statement. It cannot be reasoned around, hallucinated, or skipped.
- **Iteration is targeted and predictable.** When a request is misread or a policy changes, the fix is local: edit the extraction prompt, add a branch, adjust one API call — and you know what the next request of that shape will do. With an agent, your tools are blunter. You edit a system prompt and hope. Hoping doesn't scale, and it doesn't survive a code review.
- **Auditability comes for free.** Every step after extraction is ordinary code. You can log it, test it, and trace it exactly like any other software. When something goes wrong, you know where to look.

These advantages are real, and for a bounded process like Bob's they are decisive. The trouble starts when the process is not as bounded as the toy example makes it look.

## My real problem wasn't bounded

Our production support system was messier than Bob's laptop order. We labelled and analysed roughly 2,300 historical tickets with an AI-assisted, iterative process, and the distribution behaved exactly as the theory predicts: most of the volume fell into a handful of broad customer intents. That looked like a green light for the workflow-first approach.

But a concentrated top level did not produce a small workflow. To respond precisely, each broad intent had to be split into ever more specific [sub-intents](/post/first-level-support-automation#step-1-intent-recognition). Reaching an intent leaf was only the beginning: it then combined with the possible [fetch results](/post/first-level-support-automation#step-3-fetch) and the customer's state, and the resulting [plan-generation tree](/post/first-level-support-automation#step-4-plan-generation) grew enormous. Every iteration improved the paths we knew about, and production kept surfacing paths we didn't: new sub-sub-intents, unseen DAG combinations. The head of the distribution was concentrated; the tail was deep — and the tail is where support actually lives.

The loop I built to keep up was, ironically, the very thing the intro says business problems lack. We ran the system in shadow deployment — its responses were graded by subject-matter experts but never shown to customers — so a wrong answer had almost no blast radius. That gave me the two ingredients coding agents rely on: cheap, reversible retries and an automated signal. On top of it I ran an agentic loop that pulled the experts' free-text feedback, implemented the fix (usually a new DAG branch), added the case to an eval set, and re-ran the whole suite against it. Building the workflow had itself become an ideal task for an agent.

But notice what that loop was actually doing: using an agent to *extend a hand-coded tree*, one newly-seen path at a time. It made the workflow maintainable; it did not make the problem bounded. Every fix was reactive — a branch added *after* production surfaced a path I hadn't anticipated — so I was always one step behind the long tail, growing the tree forever without ever catching up.

## I didn't give the agent a fair chance

We did try a more agentic planner for a while. But the client had about twenty established message templates and complained when responses didn't match them, so we spent our effort prompt-tuning the agent to reproduce fixed wording — a deterministic job an agent is badly suited to. Judged on template conformity, the workflow won easily.

That comparison was unfair to the agent in two ways, though I didn't see it clearly at the time. First, the workflow had a built-in head start: we had constructed its intent tree by analysing thousands of historical tickets, so all of that knowledge was already baked into the code — while the agent was never given access to those tickets to search. Second, we judged the agent on the wrong thing: whether its reply matched one of the fixed templates, not whether it actually resolved the customer's problem. An agent that wrote a clearer, more helpful answer in its own words would still "lose", simply because it didn't reproduce the template. In short, we asked the agent to be a worse workflow instead of letting it be a better agent.

## The bitter lesson

Rich Sutton's [*The Bitter Lesson*](http://www.incompleteideas.net/IncIdeas/BitterLesson.html) (2019) argues that, across the history of AI, general methods that scale with computation — search and learning — keep beating systems that carefully encode human knowledge. The hand-built structure feels good and wins in the short run; the general method wins as compute grows.

Our enormous intent-and-plan tree is exactly the kind of hand-encoded human knowledge Sutton warns about. Every hardcoded branch was a bet that we could enumerate the world faster than the world could surprise us — and on the long tail, we kept losing that bet. The agentic alternative, given the ability to search resolved tickets and reason over them, is the general method: it leverages retrieval and model capability instead of our hand-drawn DAG. As models get cheaper and better, that side of the trade keeps getting stronger. Betting everything on the tree may have been betting against the trend.

## What I would do differently

I would give the agentic planner a real chance before growing the workflow. And I already had the perfect harness for it: the shadow deployment and eval loop I used to grow the DAG would let an agent explore just as safely — small blast radius, graded feedback, cheap retries. Instead of pointing that loop at extending a tree, I would point it at an agent. Concretely: a privacy-safe way to search resolved historical tickets, retrieval of relevant examples and templates, and deterministic business tools it can call. Templates would be examples to draw on, not wording to reproduce — mandatory only where exact wording is legally required. On the long tail, that might well have produced better outcomes even when the replies drifted from the familiar templates.

The hard constraints would still live in code: legal language, policy checks, escalation rules, permissions, and anything irreversible. The agent adapts everything else to the case. And I would evaluate what actually matters — correctness, policy compliance, tool use, resolution quality — rather than superficial template conformity.

Then I would let production evidence decide what to freeze. Frequent paths and high-consequence actions move into workflows; the long tail stays agentic. This is the progression in Will Larson's [Building internal agents](https://lethain.com/agents-series/) series, and it inverts the order I actually followed: start with the agent to discover the shape of the problem, then harden the parts that have stopped surprising you into code.

So the honest version of this post is not "workflows beat agents". It is about sequencing. Use an agent to explore the uncertain space and let it show you the real distribution of the work. Then turn the repeated and high-consequence paths — and only those — into code.
