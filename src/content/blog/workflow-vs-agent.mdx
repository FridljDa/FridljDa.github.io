## TL;DR
The first design question in an LLM automation is where each decision lives: in code or with the model. On a support automation for a bank, we put nearly all of them in code, for one good reason and one bad one. The good one: a security check has to come before any unlock, every time. The bad one: replies were graded on whether they matched the bank's templates, a test only code passes every time. The workflow we built answered the common requests and ran out on the rest, because it needed a rule for every kind of request on every state an account could be in. The security check never needed the workflow; it fits inside the unlock tool. Next time I would put the rules that must always hold in the tools, let an agent decide what to do next, and move a request type into code only once it is common and the agent gets it wrong, or the action can't be undone.

## A good reason for code, and a bad one

<DecisionMap preset="agent-first" />

Customers wrote in to our first-level support team at Northstar Bank with messages like this:

<ThemedImage src="/images/blog/the-missing-test-suite/customer-message.png" alt={"Customer message: Hi, I'm Alex Carter and I bank with your Riverton branch. My account number is NSB01234 and I can't get in any more; it keeps saying the account is locked. Can you help me get back in?"} />

The running example is based on a real project, but the details have been changed to protect the client's privacy.

To answer Alex, something has to decide what Alex wants, which account is theirs, whether it is safe to help, and what to send. Each of those decisions can live in code or with the model.

The first design we tried left all of them with the model: a single support agent that held every tool (account lookup, security-flag check, send unlock instructions, escalate to security) and wrote the reply itself.

Nothing in that design guarantees that the agent checks the security flag before it sends unlock instructions. That would be an expensive mistake. And if the model chooses the order, a customer's message can talk it out of the check: that is [prompt injection](/post/prompt-injection). As the ServiceNow CEO [put it](https://open.spotify.com/episode/11xeL3QCAF77z1vxOp0am0?si=fc70f33f0dd64ab4): people forgive other people for making mistakes. They don't forgive software. That was the good reason to put code in charge. It is also a narrow one: a single rule about the order of two tool calls.

In practice, a different complaint drove the decision: stakeholders said the agent's replies didn't match the established message templates. We tried to fix that with prompt engineering, but asking an LLM to be reliably deterministic works against its nature.

That was the bad reason. No test can tell you whether a reply to Alex is right, the way a test suite tells a coding agent its code works. Someone who knows the bank has to read it; [The Missing Test Suite](/post/the-missing-test-suite) makes the longer argument. Whatever the people reading the replies check for becomes the specification, and here it was template match. On that test code wins by construction, because code picks the template, and an agent can only lose. The grading, more than the task, picked the architecture.

## For a locked account, the workflow was right

<DecisionMap preset="workflow" />

We labelled and clustered a sample of past tickets with [an AI-assisted, iterative process](/post/snakemake-ticket-analysis-pipeline). A handful of intents accounted for the large majority of them, which encouraged us to try a workflow.

It kept code in charge of the sequence and gave the LLM one job: reading the message. The LLM recognises that Alex's is an *account-locked* request and pulls out the identifier, the account number or the name and branch. Everything after that is a small decision tree in code: look up the account, check the flag, then send the unlock-instructions template or escalate to security. The flag check comes before any unlock instructions, every time, and the reply matches the template because code chose it.

For this request it was the right design. The logic is explicit and the cases are few: the account is flagged or it isn't. The LLM's part is narrow enough to test on its own: you can build targeted evals for it, iterate on the prompt, drop to a cheaper model, or swap the extractor for a Named Entity Recognition model. When a message is misread or a policy changes, the fix is local, and you know what the next message of that shape will do.

The full version of this pattern is the four-step pipeline in [Architecture of a First-Level Support Automation](/post/first-level-support-automation); the typing that holds its seams together is in [Type-Safe Hybrid Workflows with Pydantic AI](/post/pydantic-ai-type-safe-hybrid-workflows).

## A workflow needs a rule for every cell

<DecisionMap preset="tree" />

We ran the pipeline in shadow deployment: it drafted a reply to every incoming ticket, subject-matter experts graded the drafts, and nothing went to a customer. Each round of their feedback landed a new branch in the tree, and for a while that worked.

But a workflow is only deterministic if it maps every combination of intent and [fetched data](/post/first-level-support-automation#step-3-fetch) to a reply. That mapping is a grid: every kind of request against every state its record can be in.

<DecisionFigure name="grid" />

*Three intents against three account states. Alex's request is the top-left cell; had Alex's account been closed, it would be the top-right one.*

Every question mark is a business rule someone has to decide, write down and keep current. Even this three-by-three toy leaves seven open, and we had many more than three of each. A handful of intents covered most *messages*, not most *cells*: each intent still fanned out across every state its record could be in, and every new state meant another branch and another template. The branches grew faster than the share of tickets the tree could answer.

In a running tree, a question mark isn't even a blank. A tree asks only the questions someone wrote into it. Account locked's tree in [the architecture post](/post/first-level-support-automation#step-4-plan-generation) asks whether a record was found, whether there is exactly one, and whether it is flagged. A tree like that, with no question about whether the account is open, would send a closed account the unlock steps, because nothing in it knows to ask. An agent reading the same record would at least see that the account was closed.

## The agent got the leftovers

<DecisionMap preset="fallback" />

Eventually the workflow just wasn't expressive enough, so we bolted an agent onto the tree as a fallback for the requests it couldn't cover, the ones that landed in an "Other" leaf ([the fallback in the plan-generation step](/post/first-level-support-automation#step-4-plan-generation)). Code stayed the default. A locked account like Alex's had its own branch, so the agent never saw one. It got only the scraps the code hadn't reached yet, and each new branch took some of those away.

The grading still worked against it. We scored drafts on template match rather than on whether the customer's issue got resolved. So an agent that wrote a clearer, more helpful answer in its own words still scored badly, purely for departing from a template. We were asking the agent to be a worse workflow. A score like that is [a proxy for a proxy](/post/approval-rate-is-not-savings), one step further from the outcome anyone is paying for.

## Rules that must hold belong in the tools

<DecisionMap preset="guards" />

Go back to the good reason. The rule was never that code must decide the order of every step. It was narrower: no unlock instructions go to a flagged account. A tree is one way to enforce that. A check inside the unlock tool is another: the tool reads the flag itself and refuses if it is set, whatever the agent asked for and whatever the customer wrote. That is still code deciding the order, but for one rule only, and on every path, the agent's included.

<DecisionFigure name="unlock-tool" />

*The flag check inside the unlock tool. Whoever calls it, a flagged account gets no unlock steps.*

Our pipeline already had one rule of this kind: plans involving money, account access or side effects required [human review](/post/temporal-human-in-the-loop). Neither rule needs a tree around it.

So a reply to Alex involves two kinds of decision. Some are rules that must hold every time: check the flag before an unlock, get a person's approval before anything that can't be undone. Those belong in code, inside the tools, where no message can talk the model past them. The rest is choosing what to do next: which record is Alex's, which tool to call, what to say and what to ask. That is the part the tree kept failing to write down, and it is the part a model is for.

Templates fall on both sides of that line. A sentence every reply must contain, for legal reasons say, is a rule, and the send tool can add it. Matching a template for its own sake is choosing what to say; grading on it is how we ended up with a tree.

## Next time: make the agent the default

<DecisionMap preset="next-time" />

Next time I would invert the default, following Will Larson's [Building an internal agent](https://lethain.com/agents-coordinators/), which starts every workflow with the LLM in charge. The agent decides what to do next and acts only through tools that enforce the rules. A request type graduates into a path in code only once it shows up often and the agent handles it unreliably, or when the action is irreversible enough that you don't want a model deciding it at all, not even behind a guard.

For Alex, that would go like this. The agent reads the message, looks up NSB01234 and asks the unlock tool to send the instructions. The tool checks the flag first. If the account isn't flagged, Alex gets the steps; if it is, the tool refuses and says why, and the agent escalates to security. If locked accounts turned out to be common and the agent kept getting them wrong, Account locked would graduate into a path in code like the one above. Until the grades say so, nobody writes it.

It is also the shortest path into shadow deployment. An agent with a set of tools is much less to build than a tree of intents, plans and templates, and every week before the experts see real drafts is [a week of grades lost](/post/the-missing-test-suite#get-into-shadow-deployment-sooner).

## The agent still doesn't know the bank

<DecisionMap preset="rules" />

Inverting the default doesn't shrink the grid. It spares you enumerating it, which is exactly where we hit the wall, but skipping a cell is not the same as answering it correctly.

The agent arrives no better informed than the tree did. No model was trained on Northstar's escalation rules or on Alex's account. A read tool lets the agent look up Alex's record, but what to do about a closed account depends on the bank's rules, and a read tool only helps with the rules somebody wrote down. Usually nobody has: they live in the heads of the people who answer the tickets.

The obvious shortcut is to point the agent at resolved tickets, and it isn't a clean fix. They are full of resolutions that contradict each other and current policy; the tree, for all its gaps, was at least a single curated source of truth. They are also full of personal data, and an agent that retrieves and reasons over them is a far larger privacy and security exposure than a fixed tree.

## Let the experts decide what goes into code

<DecisionMap preset="start" />

Neither design tells you which cells of the grid matter. A workflow makes you guess them up front; an agent lets you skip writing them down. Only the people who know the business can settle which paths are worth freezing into code, and they settle it by grading the system's drafts. What they grade for decides the outcome. Graded on template match, code wins every time, whatever the customer needed. Graded on whether the customer's problem was solved, the drafts show where the agent goes wrong, and those are the cells worth writing down.

If I built this again, I would first [work out what the automation would actually save](/post/approval-rate-is-not-savings). Then I would write the rules that must always hold into the tools: the flag check inside the unlock tool, and human review in front of anything that can't be undone. I would put the simplest agent that can draft a reply behind a shadow deployment and [get the experts grading](/post/the-missing-test-suite) whether each draft solves the customer's problem. A request type would move into code only when their grades show it is common and the agent gets it wrong, or when its action is one no model should choose. The rules live in code, the judgement lives with the model, and the experts decide where the line between them goes.
